Design system audit agent

I coached a senior product designer and a product designer to build an agent that reads every Figma file at Best Egg, counts each button variant, maps where it’s used and flags what to cut. It turned one overloaded button component into three, and an internal design system site now rebuilds itself from Figma every week.

Outcome

86%

Fewer button variants: from 2,304 in one component to 321 across three

Role
Director of Product Design
Team
1 senior product designer, 1 product designer
Timeline
1 quarter
Launched
Q2 2026

My role

The method

I decided to run the audit as an agent instead of by hand, and I wrote its brief and the rules it worked to: read every file, list every variant, find every instance, flag anything unused or duplicated and show its working. Buttons went first because they were the visible mess. I drove the work and the senior product designer and product designer executed it.

The coaching

The senior product designer built the agent, and I coached the pair through it: how to brief it, how to read its list against the files, when to overrule it. Its count was a claim until we checked it, so both ran it and we reviewed the list as a group, then decided the split into three components together. They then had the agent write the guideline and the library to the calls we had made.

The audience

I presented the work to product leadership and then to the product org: the reduction, the time saved and what it did to the workflow. New product designers ramp faster on three components than on one that did everything, and engineering can see the button styles instead of guessing between them. Leadership asked for the same run on their own use cases.

Results

The old .Button carried seven properties multiplied together, and most of the results were never used. I set the direction and the senior product designer and product designer shipped Button, Icon Button and Link, with icons and fixed widths handled inside the component instead of as variants. The counts are the Figma library’s own, before and after.

The problem

One component, .Button, held seven properties: style, color, size, icon, fixed width, state and theme. Multiplied out, that was 2,304 variants, most of them unused and many near-identical. It was confusing, it was frustrating, and it was hard to tell which button was the correct one.

  • CoverageThree components still had to cover every real use in the product.
  • TrustThe team had to believe an agent’s count over its own sense of what was in the file.
  • AdoptionA new structure only counts once product designers use it.

The design

The agent ran through every Figma file: it listed each variant, found every instance in the product files and flagged what was unused or duplicated. The senior product designer and product designer ran each pass and brought the list to me. As a group we kept 321, split them into Button, Icon Button and Link, and had the agent write the usage guideline.

Split by purpose

Button, Icon Button and Link each got their own component, so the name says what it is for.

Booleans over variants

Left and right icons became toggles and the icon itself a swap, so they add nothing to the matrix.

One disabled state

Danger, Brand and Action reuse Primary’s disabled variant instead of defining their own.

The library

With the set settled, we had the agent build an internal design system site: every component rendered live, with its props, code and tokens on one page. It reads the component library in Figma and updates every week, so what the site shows is what the file holds.
